# Limitations and known risks (current)

**Languages**: C (`.c`, `gcc -std=c11`, `-lm` linked) and C++ (`.cpp .cc .cxx .C`, `g++`) are supported; the language is chosen by file extension (case-sensitive: `.C` is C++). Settings: `dsv.cCompiler`, `dsv.cStd`, `dsv.extraCFlags` for C; `dsv.compiler`, `dsv.cppStandard`, `dsv.extraCompilerFlags` for C++.
- The allocation shim is C++ and is always built with `dsv.compiler` (`g++`), even for C programs, so `g++` must be installed. It links `libstdc++` into the traced C program (it logs exactly the program's own allocations; checked).
- **Anonymous struct/union members** are read and shown as members of the enclosing aggregate (as C exposes them), at any nesting depth. A *named* member of an anonymous type (`struct { int x, y; } pos;`) is a field of its own, but its type is shown as `struct {...}`. Name clashes between an anonymous member's fields and the enclosing ones cannot occur in valid C/C++.
- **Strings**: a `char*`/`const char*` value carries the text it points at (`PointerValue.str`, <= 40 chars, printable ASCII; unreadable or binary memory gives none) and is shown as `"text"`; `char[]` arrays are drawn as characters (`\0` for NUL), and a `char[N]` member holding text is the node's label (when named name/title/word/text/str/label/key/id and no better key) or an extra field instead of a separate numeric array. `std::string` has its own reader. Only `char` pointers are decoded (not `wchar_t`, UTF-8 beyond ASCII).
- C type names are canonical: a struct with a tag is shown by its tag however it is spelled (`struct Node`, `Node`, a typedef of it); an anonymous `typedef struct {...} Name;` is shown as `Name`.

**Platform**: Linux only (GDB + `LD_PRELOAD`). macOS/Windows return an explicit error. An LLDB backend behind `DebuggerBackend` is future work;
LLDB/Clang were not installed here and nothing was tested with them.

**Tracing**
- Heap objects come from the glibc malloc family (`malloc`, `calloc`, `realloc`, `reallocarray`, `free`, `memalign`, `aligned_alloc`, `posix_memalign`; `operator new/delete` go through it), logged by the `LD_PRELOAD` shim. Requires glibc (the shim calls `__libc_*`). Only the root process is logged: forked and exec'd children are not. Not tracked: `mmap`-based allocators, custom arenas, `unique_ptr` internals' *types*, stack objects. `realloc` is one record (`R old new size`); the tracer keeps the learned type of the block whether it grew in place or moved. A moved-from block is reported freed, like `free()` (drawn as a dashed ghost only while a pointer still refers to it).
  Allocations made before `main` (e.g. by global constructors) are kept on purpose: they are user data. Only blocks whose type was learned from a typed pointer are drawn or counted in findings, so untyped runtime buffers (such as stdio's) never show up.
  `unique_ptr`/`shared_ptr`/`weak_ptr` values are turned into the raw pointer they hold when the trace is parsed (`normalizeSmartPointers`, core), so adapters follow them like `T*`. `std::make_shared<T>` allocates one block (control block with `T` inside): when a `shared_ptr`/`weak_ptr`'s pointer lies strictly inside its own control block the tracer registers `T` as a synthetic allocation nested in the block (`register_inplace`; state follows the block, so after `T`'s destructor ran while a `weak_ptr` keeps the block alive its contents are stale, not marked freed). Control blocks themselves (`_Sp_counted_*`) are never drawn. Only pointers held in a `shared_ptr`/`weak_ptr` object trigger this: a raw `T*` obtained from `get()` is seen once some smart pointer to the same object has been read. `std::vector` and `std::string` have their own readers (below: other containers).
- **STL containers (M8, logical view)**: `std::map multimap set multiset list` (node walk, validated), `std::deque` and `unordered_map unordered_multimap unordered_set unordered_multiset` (pretty-printer for the values, memory walk for identity/chunks/buckets). Shown as a sequence of elements in iteration order; `unordered_*` also show `bucket_count`. `map multimap set multiset list deque unordered_*` also have an **Internal** view (a Logical | Internal switch in the scene caption, remembered per container name for the session): for the associative ones the red-black tree with node colours, linked exactly as `_M_parent/_M_left/_M_right` say; for `list` the doubly linked nodes (links are drawn from the validated walk order: the tracer checks every `_M_prev` against the preceding node, so they equal `_M_next/_M_prev`; the sentinel is not drawn; for `unordered_*` the bucket table with its node chains: libstdc++ keeps all nodes in one singly linked list and `_M_buckets[j]` points at the node *before* bucket j's first node, so membership is read from memory and validated, not recomputed from a hash; values still come from the pretty-printer and are matched to nodes by position and address; the cross-bucket `_M_nxt` links are not drawn, and more than 2048 buckets is refused). It exists only when the whole container was walked (<= 200 elements, default allocator, all checks passed); otherwise the switch is disabled and its tooltip gives the reason. For `deque` the internal view is the chunk map (`_M_map[r]` -> chunk r) with the slots in use; element addresses are the identity (they do not move on push/pop at the ends); validated against `size()`, chunk allocations and the printer's element addresses; requires the default allocator and at most 200 elements.
  - `std::stack` and `std::queue` over a `deque` are drawn as a stack/queue scene (top / front / back pointers) under the variable's name; over a `vector` (or `std::priority_queue`, always a vector) they are array scenes named after the variable (a priority_queue is a heap by name). `std::array` is an array scene named after the variable. Other adapter containers (`flat_map`, custom wrappers) appear as plain structs.
  - At most 200 entries per container per step are read (`DSV_MAX_STL_ELEMS`); the true `size()` is kept and the drawing ends with a "+N more" box. Elements are consumed lazily, never the whole container.
  - **The node walk requires the default `std::allocator`.** `pmr`/custom allocators fall back to the pretty-printer: contents are right but entries are identified by key (map/set) or position (list) instead of node address, so insertions animate less well.
  - **The node layout was checked against** (a) libstdc++ 6.0.36, GCC 16.2.1, GDB 18.1 (Fedora 45) and (b) Ubuntu 24.04 on `ubuntu-latest`: `g++` 13.3.0 headers, runtime `libstdc++6` 14.2.0 (`libstdc++.so.6.0.33`), GDB 15.1; and (c) Ubuntu 22.04 in a container: `g++` 11.4.0, libstdc++ 12, GDB 12.1 (97 of 99 tests; the 2 bwrap tests skip because containers cannot create namespaces). The whole suite incl. the node-walk validation passes on all three. Any other libstdc++ (older than GCC 9, other distributions) is untested. Offsets come from DWARF, not constants; if a field is missing or any check fails (node not a live allocation, links disagree, count != `size()`, walk disagrees with the printer on the first entries) the container silently drops to the printer and says why in `internalError`.
  - Without the libstdc++ printers (not auto-loaded and no `/usr/share/gcc*/python/libstdcxx`): map/set/list still work (node walk, no cross-check); deque and `unordered_*` show an explicit "pretty-printers are not available" note and the raw text. libc++ and MSVC containers are not supported (Linux + libstdc++ only).
  - Pointers *inside* elements are shown as addresses (the pointee is still tracked and drawn by its own adapter); no edges are drawn from a container element (or an array cell) to it, because scenes are separate drawings; instead such cells carry a `ref`: clicking one selects the pointee in whichever scene draws it (and cells that point at the selected object are outlined). Libstdc++ iterators (`it`, a range-for's `__begin`) are shown as text, not followed.
  - A container that is not constructed yet (declaration not executed) or already destroyed reads as "contents not readable" rather than garbage.
- Builds are forced to `-O0 -g -fno-inline`. Optimised or inlined code is not supported.
- A `step` that never returns (a loop whose whole body is on one line and never changes line) is interrupted by a watchdog after
  `DSV_STALL_SECONDS` (3s) and reported as `stalled`; the trace up to that point is kept.
- **Sub-line stepping (M9)**: a source line with several statements (`tmp = a; a = b; b = tmp;`, a comma expression, `a = g(a); b = g(b);`, a one-line loop body) is shown as several stops (`Step.sub` = 1, 2, ...), one after each DWARF line row (statement), found with internal breakpoints at the rows. Rows (with columns and discriminators; GDB's own line table drops the discriminator rows) are read from the program's DWARF line program with the vendored pyelftools 0.33 (`engine/vendor/pyelftools`, public domain, **needs Python >= 3.10 in the interpreter embedded in gdb**: Fedora 45's gdb embeds 3.15, Ubuntu 22.04's gdb 12 embeds 3.10, 20.04's 3.8 would not work), once per run (`engine/debugger/linetable.py`); if pyelftools cannot be imported (old Python), the DWARF cannot be read, or the rows disagree with GDB's, the run is not failed: lines are read whole and the reason is in the end record (`subStep.note`) and on stderr. No `objdump`/`readelf` is needed. Stops where nothing changed are dropped. A line whose sub-stops were all dropped as unchanged in 8 consecutive executions of it (`DISARM_AFTER`, a constant) is disarmed for the rest of the run and listed in `subStep.disarmedLines` (executions with no stop at all do not count). Budgets: `dsv.maxSubStepsPerLine` (64; dropped stops count; a line over it is read whole from then on and listed in `subStep.truncated`) and `dsv.maxSubStepsPerRun` (5000); `dsv.subSteps: false` turns it off. Writes inside a callee are not split: the callee's own lines are traced as usual and the caller gets a stop after the call returns. Nothing in it is x86-64 specific (DWARF + breakpoints); on other architectures it is enabled but logged as "not verified" (only x86-64 was tested).
  - **Loop headers are not split.** A line that holds only a `for`/`while` header (body on other lines; also the continuation line of a header split over several lines) is not armed: its init/condition/increment stops only repeated the body's first state (measured: 1004 of 1058 sub-stops in a 300-node list benchmark, +59% trace time). The test is on the source text with `//` and `/* */` comments removed (`is_loop_header` in `engine/debugger/linetable.py`); a one-line loop (`for (...) { a += i; }`) is still split. Stops that turn out unchanged are dropped but still count against both budgets (`subStep.droppedByLine` in the end record names the worst lines): a body line whose second row is hit before anything changed (`sum += c->val;`) costs a snapshot per iteration until it is disarmed after 8 (benchmark: 318 dropped stops became 26).
  - **Column highlight**: on a split line the editor marks the statement about to run (and the one that just ran, when on the same line) instead of the whole line. GCC's column is that of the statement's operator, so the range is widened by a text heuristic (`statementRange`, `core/explain/columns.ts`: up to `;` `,` `{` `}` or an unmatched bracket); odd formatting (a statement spanning lines, macros) can give a wrong range, a missing or 0 column marks the whole line.
  - **A line is split only where the compiler emitted a row per statement.** Not split: several writes inside *one* statement (`a = b = c = 5`, `x = y = z`, `a[i++] = i`, a struct/array copy or `memset`, `p->a = p->b = 0`): they show as one change. Splitting those needs instruction stepping (design B in `docs/architecture.md`), not built.
  - Sub-stepping applies to a line from its start; after a call into traced user code the rest of the line is split again only for rows after the call returns (the context survives the callee). The per-line read is otherwise unchanged: reads are per stop, not per write.
- **Globals**: file-scope and `static` variables of the user's source are read every step (pseudo-frame `(globals)`, shown as "globals" in the Variables panel and used like locals by the adapters: a global `Node* head` is a named pointer, a global array/vector/map is drawn). Library globals (`std::cout`) are not read; a global's initial value is its value at `main` (constructors of globals have already run). Globals declared in headers the user wrote are included only when the header is the source file itself.
- Objects reachable from stack pointers are discovered when first seen through a typed pointer; an allocation that is never referenced by a
  typed pointer (e.g. only through `void*`) is not drawn. Pointer-typed values pointing at *garbage that happens to fall in a live allocation*
  are reported as pointing there (that is what memory contains).
- Cost: roughly 5-20 ms per step; the default cap is 20000 steps (`dsv.maxSteps`). The whole trace is held in memory (expanded frames share unchanged values by reference) and sent to the webview. On disk/wire frames are delta-encoded (schema v4).

**Recognition** is heuristic (field names, field types, observed back-links). Unusual designs (sentinel nodes, arrays-as-trees with unusual names,
intrusive lists) may be classified as `generic` or with low confidence. Heap vs. array detection uses names (`heap`, `queue`, `stack`, `hash`, `graph`).
Array cells of struct/`pair` elements show a key-like field (`key first val value data id to x k v name`, else the first scalar) as the label and the other fields below, full content on hover; a heap is recognised by name for scalar *or* struct elements. `std::vector` iterators (`__gnu_cxx::__normal_iterator`, e.g. a range-for's hidden `__begin`) are shown as text and no longer pull the vector's storage in as a second scene. Index markers on arrays are integer variables with index-like names. A `new[]` array is titled after the variable that points at it (`a → int[6]`, `s.data → int[4]`; outermost frame wins), else by type and address.

**Security**: user code is compiled and run. Protections: separate process group, wall-clock timeout, CPU `ulimit -t`, address-space `ulimit -v`
(`dsv.maxMemoryMB`), output caps, step cap, and, for the **traced run** (`dsv.sandbox: auto`, default), bubblewrap when it is installed and works (probed once at startup):
read-only filesystem, private `/tmp`, `$HOME` replaced by an empty tmpfs (the engine and the source's directory stay readable), and new network/PID/IPC/UTS/user namespaces,
so the program cannot write outside its work directory, read dotfiles or keys in `$HOME`, or reach the network (tested with a hostile program). Without `bwrap` (not installed, or
unprivileged user namespaces disabled, e.g. Ubuntu 24.04 AppArmor default) it falls back to a new network namespace via `unshare -r -n` (`dsv.isolateNetwork`), and if that fails to nothing.
**Still not a hard boundary**: no seccomp filter, the rest of the filesystem is world-readable to the user (`/etc`, `/var`, other users' readable files), the *compile* step is not sandboxed
(`#include "/path"` can read files into diagnostics), and a kernel/namespace escape defeats it. Only trace code you trust.

**Analysis**: static complexity estimates are regex-level and labelled as estimates. Findings (leak, dangling, crash) come from the recorded run only.
No LLM is used; `ExplanationProvider` is the extension point, and providers receive only recorded facts.
